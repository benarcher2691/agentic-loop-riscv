# Tasks

Ordered. The loop agent takes the **first unchecked** task each iteration. Every task ends with
`make check` green (all benches PASS, synth without latches, fits the hx1k at 12 MHz) and a commit.
Architecture target, so no task requires rewriting an earlier one: `SOC` (clock, reset, IO) →
`Processor` (CPU) + `Memory` (RAM/ROM), plus small pure modules `Decoder`, `ALU`, `Clockworks`.

- [x] **Hardware fix: hold reset until the block RAM is ready.** On the real iCE40 the block RAM contents are not readable for a while after configuration (Lattice: several microseconds; the reference design waits 2^16 clocks). `Clockworks` releases `resetn` after 16 CLK cycles (1.3 µs), so on the board the CPU fetches garbage from the program BRAM and executes it: LEDs stay dark and no banner is sent, although every simulation passes (simulated BRAM is ready at time 0). Fix in `rtl/clockworks.v`: add `parameter RESET_CYCLES` — **65536 by default (hardware)**, and `16` under `` `ifdef FAST_SIM `` (so every bench keeps its timing) — implemented as a counter that sticks at its terminal value. Update `tb/clockworks_tb.v`: keep the existing 16-cycle checks (FAST_SIM) and add one instantiation with `#(.RESET_CYCLES(64))` that checks `resetn` is low for exactly 64 CLK cycles then high forever. Also confirm (with a check) that `Processor` holds `PC = 0` and `state = FETCH_INSTR` and that `SOC` holds `LEDS = 0` while `resetn` is low. No other functional change; `make check` must stay green (equiv included).

- [x] **Blinker.** `rtl/clockworks.v`: `Clockworks #(parameter SLOW = 0)(input CLK, output clk, output resetn)` — `clk` is `CLK` divided by 2^SLOW (SLOW = 0 passes CLK through); `resetn` is a power-on reset: low for the first 16 `CLK` cycles after power-up, then high forever (no reset button on the board). `rtl/soc.v`: `SOC #(parameter SLOW = 19)` instantiates `Clockworks`, and a 5-bit counter driven by `clk` and cleared by `!resetn` drives `LEDS`. Benches: `tb/clockworks_tb.v` (SLOW = 0 → clk follows CLK; SLOW = 3 → exactly one `clk` edge per 8 `CLK` edges over 64 cycles; `resetn` timing) and `tb/soc_tb.v` with `SOC #(.SLOW(0))`: LEDS = 0 during reset, then increments by exactly 1 per clock, wraps 31 → 0.

- [x] **LED patterns from ROM.** `rtl/memory.v`: `Memory(input clk, input [31:0] mem_addr, output reg [31:0] mem_rdata, input mem_rstrb)` — `reg [31:0] MEM [0:255]` (1 KB), synchronous read of `MEM[mem_addr[9:2]]` when `mem_rstrb` is high, initialised in an `initial` block. `SOC` gets `reg [31:0] PC` (starts at 0, advances by 4 each `clk`, wraps after the last initialised word) and shows `mem_rdata[4:0]` on LEDS. Bench: `tb/memory_tb.v` (read strobe, word addressing, rdata holds when strobe low) and `tb/soc_tb.v` checks LEDS follow the ROM word by word for two full passes against the same constants the ROM was initialised with.

- [x] **Decoder, part 1: opcode classes and register fields.** `rtl/decoder.v`: purely combinational `Decoder(input [31:0] instr, …)` with outputs `isALUreg, isALUimm, isBranch, isJALR, isJAL, isAUIPC, isLUI, isLoad, isStore, isSYSTEM` (one-hot over the 10 RV32I opcode classes, all zero for any other opcode), `rs1Id, rs2Id, rdId` (5 bits), `funct3` (3), `funct7` (7), plus the immediate outputs `Iimm, Simm, Bimm, Uimm, Jimm` (may be left for part 2 but must be declared and driven). An `rtl/decoder.v` may already exist from an interrupted session: verify it, do not rewrite it. Bench `tb/decoder_tb.v`: 10 hand-encoded instructions, one per class (e.g. `add x3,x1,x2` = `32'h002081B3`, `addi x1,x0,5` = `32'h00500093`, `ebreak` = `32'h00100073`), each checking all ten class flags and the register/funct fields. Keep the bench small and direct; it grows in the next two tasks.

- [x] **Decoder, part 2: I, S and U immediates.** Sign-extended exactly as the RISC-V spec defines them: `Iimm = sx(instr[31:20])`, `Simm = sx({instr[31:25], instr[11:7]})`, `Uimm = {instr[31:12], 12'b0}`. Extend `tb/decoder_tb.v`: positive and negative I immediates (`addi x1,x0,-1` = `32'hFFF00093` → `Iimm = 32'hFFFFFFFF`), `lw` and `sw` with positive and negative offsets (`sw x2,-4(x1)` = `32'hFE20AE23` → `Simm = -4`), `lui x5,0xFFFFF` = `32'hFFFFF2B7` (bit 31 set). Check every immediate output on every vector (the ones that do not apply still have a defined value — check it too).

- [x] **Decoder, part 3: B and J immediates + assembler cross-check.** `Bimm = sx({instr[31], instr[7], instr[30:25], instr[11:8], 1'b0})`, `Jimm = sx({instr[31], instr[19:12], instr[20], instr[30:21], 1'b0})`. Extend the bench: forward and backward `beq`/`bne` (`bne x1,x2,-8` = `32'hFE209CE3` → `Bimm = -8`), forward and backward `jal` (`jal x0,-8` = `32'hFF9FF06F`), plus a cross-check loop: for at least one instruction per class, build the word with the `RType/IType/SType/BType/UType/JType` functions from `lib/riscv_assembly.v` (include it inside the bench with a small `MEM`) and check that the decoder recovers the fields and immediates you passed in.

- [x] **ALU.** `rtl/alu.v`: combinational `ALU(input [31:0] in1, in2, input [2:0] funct3, input funct7_5, output [31:0] out, output EQ, LT, LTU)` implementing ADD/SUB (SUB when `funct7_5`, funct3 = 0), SLL, SLT, SLTU, XOR, SRL/SRA (SRA when `funct7_5`), OR, AND with the shift amount from `in2[4:0]`; `EQ`, `LT` (signed), `LTU` compare `in1` vs `in2` for later use by branches. Bench `tb/alu_tb.v`: for every operation, edge values (0, 1, −1, `0x7FFFFFFF`, `0x80000000`, shift by 0/1/31) plus ≥ 200 pseudo-random vectors (`$random` with a fixed seed), each checked against a behavioural reference in the bench using Verilog operators and `$signed`.

- [x] **Processor, part 1: fetch, register bank, ADDI, halt.** `rtl/processor.v`: `Processor(input clk, resetn, output [31:0] mem_addr, input [31:0] mem_rdata, output mem_rstrb, output [31:0] x1)`. `reg [31:0] RegisterBank [0:31]` with `x0` always reading 0; `reg [31:0] PC`; a 3-state machine `FETCH_INSTR → FETCH_REGS → EXECUTE` (assert `mem_rstrb` with `mem_addr = PC` in FETCH_INSTR, latch `mem_rdata` into `instr` and read rs1/rs2 in FETCH_REGS, write back and advance `PC <= PC + 4` in EXECUTE); uses `Decoder`. For now only `ADDI` writes `rd` (`rs1 + Iimm`); every other instruction is a NOP that still advances PC; `isSYSTEM` (EBREAK) halts: state stays put, PC frozen. `x1` mirrors `RegisterBank[1]`. `SOC`: instantiate `Processor` + `Memory` at full `CLK` speed (drop the LED counter; LEDS show `x1[4:0]`); put a small ADDI program in `Memory`'s `initial` block via `lib/riscv_assembly.v`. Bench `tb/processor_tb.v` with its own memory model and program written with the assembler macros: chained ADDIs (`ADDI(x1,x0,5); ADDI(x2,x1,7); …`), a negative immediate, `ADDI(x0,x0,5)` leaves `x0` = 0, `EBREAK` halts (PC stops changing for 20 cycles); check registers by hierarchical reference. Update `tb/soc_tb.v` for the new SOC. Keep it minimal — the other instructions are the next task.

- [x] **Processor, part 2: all register-register and register-immediate instructions.** Wire `ALU` into EXECUTE: `isALUreg` uses `rs2`, `isALUimm` uses `Iimm`; shifts take the amount from bits [4:0] of the second operand; `funct7[5]` selects SUB/SRA only where the spec allows (SUB for register ADD only, SRA/SRAI for both). Extend `tb/processor_tb.v`: every ALU-reg and ALU-imm instruction at least once with hand-computed results, `SRAI` of a negative value, `SLTIU` with `-1` (unsigned compare), `SUB` producing a negative result, `SLLI` by 31.

- [x] **Jumps: JAL and JALR.** `rd <= PC + 4`; JAL: `PC <= PC + Jimm`; JALR: `PC <= (rs1 + Iimm) & ~1`. Bench: forward and backward JAL, JALR through a register, `rd = x0` (no link written), a two-iteration loop counted in a register, link register value checked against the hand-computed address.

- [x] **Branches.** BEQ, BNE, BLT, BGE, BLTU, BGEU using the ALU's `EQ/LT/LTU`; `PC <= PC + Bimm` when taken. Bench: each branch taken *and* not taken; signed vs unsigned distinguished with `−1` vs `0xFFFFFFFF` operands; a countdown loop that sums 1..10 into a register (expect 55).

- [x] **LUI and AUIPC.** `LUI: rd <= Uimm`; `AUIPC: rd <= PC + Uimm`. Bench: LUI with bit 31 set, LUI + ADDI building a full 32-bit constant, AUIPC at two different PCs checked against hand-computed values.

- [x] **Program suite.** `tb/programs_tb.v`: complete programs with hand-verifiable results — fibonacci(10) = 55 by loop; gcd(48, 18) = 6 by subtraction loop; a subroutine using `CALL`/`RET` (ra/x1) called twice with different arguments in `a0`; nested calls that save/restore ra via `ADDI sp` + (for now) registers, since loads/stores do not exist yet. Each program ends with EBREAK; results checked in registers. No RTL change expected unless a bug surfaces — if so, fix it and add a regression check.

- [x] **Shrink the core.** `make stat` reports ~1180 of 1280 logic cells (1136 LUT4, 204 carry): six separate 32-bit adders and three separate barrel shifters. Loads, stores and the UART still need ~250 cells. Bring the whole design to **≤ 900 logic cells** (enforced: `make check` now fails above `LC_BUDGET`; aim for ~700) with **no functional change** — all existing benches are the regression and must keep passing unchanged. Techniques, in order of payoff: (1) one 33-bit subtraction `aluMinus = {1'b1, ~in2} + {1'b0, in1} + 33'd1` shared by SUB, SLT, SLTU, and the branch compares: `LTU = aluMinus[32]`, `LT = (in1[31] ^ in2[31]) ? in1[31] : aluMinus[32]`, `EQ = (aluMinus[31:0] == 32'd0)`; ADD is the only other adder in the ALU. (2) one right-shifter: `shifter = $signed({funct7_5 & in1[31], in1}) >>> in2[4:0]` gives SRL and SRA; for SLL, bit-reverse `in1` before the shifter and bit-reverse the result (a `function [31:0] flip32` — pure wiring, zero cells). (3) one adder for `PC + immediate` shared by JAL, AUIPC and branches — select the immediate (`Jimm`/`Uimm`/`Bimm`) with a mux *before* the adder; keep a separate `PC + 4`. (4) branch conditions come from the ALU's `EQ/LT/LTU` only — delete any comparator in `Processor`. Run `make stat` after each step and write the before/after numbers in `PROGRESS.md`.

- [x] **Loads.** `Memory` and `Processor` become byte-addressable: LW, LH, LB, LHU, LBU with correct byte/halfword selection from `mem_addr[1:0]` and sign/zero extension; add a `LOAD` wait state for the synchronous memory. Bench: a data area written with `DATAW`/`DATAB` from the assembler; every load type at every byte offset (0..3 / 0,2) including values with the sign bit set; misaligned halfword at offset 1 is not required.

- [x] **Stores.** `Memory` gets `input [31:0] mem_wdata, input [3:0] mem_wmask` (byte enables); SW, SH, SB write only the addressed bytes. Bench: store then load back for each width and offset; a byte store must not change the other three bytes (check `dut.MEM[i]` / the memory model directly); SW over a previous SB.

- [x] **Shrink the core, round 2.** Now that `Memory` is writable the flattened numbers in `make stat` are real. Bring the unflattened total to **≤ 950 LUT4** (budget is 1150 for now; the UART and IO decode still need ~100) with no functional change — every bench, including `equiv`, is the regression. Where the cells are: `ALU` (~490 LUT4 — a shared-subtractor/single-shifter RV32I ALU is ~250: fold the XOR/OR/AND arms into one `case (funct3)` after the shared subtractor, make sure only ONE `>>>` exists in the whole ALU, and check that `flip32` really is wiring by looking at `build/synth_noflat.log`), and the load path in `Processor` (~200 LUT4 for byte/halfword select + sign extension — select the byte with `mem_addr[1:0]` in one 4:1 mux of 8 bits, then the halfword with `mem_addr[1]` in one 2:1 mux of 16 bits, then sign-extend once; do not build separate paths per load type). Record before/after per module in `PROGRESS.md`.

- [x] **Memory-mapped IO.** In `SOC`: address bit 22 selects IO space instead of RAM. Word offsets (bit 2 → LEDS write, bit 3 → UART data write, bit 4 → UART status read: bit 9 = busy, using `corescore_emitter_uart` from `rtl/emitter_uart.v` at 12 MHz / 115200 baud). Software writes to LEDS drive the `LEDS` port. Bench `tb/io_tb.v`: a program that writes `5'b10101` to LEDS (checked on the `SOC` port) and sends "OK\n" over the UART, waiting on the busy bit; the bench contains a serial *receiver* model that samples `TXD` at 115200 baud (104.17 clocks per bit at 12 MHz, sample mid-bit) and checks the three received bytes.

- [x] **Hardware demo program.** `Memory`'s initial program: print "Loop RISC-V\n" once over the UART, then cycle a pattern on LEDS forever with a software delay loop; delay constant small under `` `ifdef BENCH `` (so `tb/soc_tb.v` can check the banner and the first three LED patterns in simulation) and ~0.25 s per step on hardware. After this task the human runs `make prog` and `make uart`.

# Phase 2 — a computer, not just a core

Same rules. The SoC currently has 1 KB RAM, UART transmit only, and no way to read time.

- [x] **UART receiver.** `rtl/uart_rx.v`: `UartRx #(parameter CLK_HZ = 12000000, BAUD = 115200)(input clk, resetn, rx, output reg [7:0] data, output reg valid)` — 8N1, two-flop synchroniser on `rx`, start-bit detection on the falling edge, each bit sampled at mid-bit (CLK_HZ/BAUD = 104.17 clocks per bit at 12 MHz), `valid` is a one-clock pulse when a byte is complete, false start bits (line back high at mid-start) are ignored. `SOC`: a new IO word at offset bit 5 (address `0x400020`): reading it returns `{23'd0, avail, data}` where `avail` (bit 8) is 1 while an unread byte is pending; the read clears `avail`. Bench `tb/uart_rx_tb.v` with a serial *transmitter* model in the bench: single bytes, two back-to-back bytes, a byte after a long idle, a glitch shorter than half a bit (must be ignored); check `data`/`valid` timing to the clock. `make stat` must stay under budget.

- [ ] **Echo program.** After the banner, the demo program loops: poll the RX word; when `avail`, write the byte to the UART data register (wait on busy) and show its low 5 bits on the LEDs. Keep the LED walk *before* the echo loop only under `FAST_SIM` is short; on hardware the walk runs once (5 steps) then the echo loop starts. Bench: `tb/soc_tb.v` sends "hi" through the bench's transmitter model after the banner and checks "hi" comes back on `TXD` and that `LEDS == "i" & 31`. The human test: `make hwtest`, then type in `screen /dev/cu.usbserial-*1 115200`.

- [ ] **6 KB of RAM.** `Memory`: 1536 words (6 KB). The hx1k has sixteen 4 Kbit block RAMs: the register file uses 2 and 6 KB needs 12, so 14 of 16. `Processor`: PC arithmetic and the fetch/load/store address path grow from 10 to 13 bits (`PC[12:0]`); everything about IO decode (bit 22) is unchanged. Benches: `tb/memory_tb.v` reads/writes words above 1 KB and at the last word; `tb/programs_tb.v` gets one program placed at address 4096 (assembled with `memPC` moved) and a data area at 5120; `make stat` reports 14 BRAMs and stays under the LUT budget (the wider adders cost some).

- [ ] **Cycle counter (RDCYCLE / RDCYCLEH).** A 64-bit free-running cycle counter readable through the CSR read encodings `csrrs rd, cycle, x0` (`0xC0002073 | rd<<7`) and `csrrs rd, cycleh, x0` (`0xC8002073 | rd<<7`): decode `isSYSTEM` with `funct3 == 010` and `Iimm[11:0] ∈ {0xC00, 0xC80}` as a counter read that writes `rd` and advances PC; every other `isSYSTEM` still halts. Bench: two reads with a known number of instructions between them differ by exactly 3 × that count (+ 1 per load); `cycleh` is 0; EBREAK still halts. Then use it in the demo program's delay loop (0.25 s = 3 000 000 cycles) instead of the counted loop — the bench checks the LED period against the counter.

# Phase 3 — hardware in the loop

The board becomes a test fixture the loop can drive over the UART. The monitor and the test programs
are built and proven in simulation by the loop (the serial models in the benches already speak both
directions); the host-side tool and `make hwcheck` are supervisor work (they need the board to test).

- [ ] **Monitor program.** The resident program becomes a monitor: banner, one LED walk, then a command loop over the UART. Binary protocol, all multi-byte values little-endian 32-bit: `V` → reply the 4 bytes `"RV32"`; `W addr len data…` → write `len` bytes starting at `addr` (any address: RAM or IO), reply `K`; `R addr len` → reply `len` bytes read from `addr`; `G addr` → call `addr` (`JALR ra`) and, when the routine returns with `ret`, reply `K` — the routine may clobber every register except `sp`, and the monitor re-establishes its own state after the return; any other command byte → reply `?`. Reading the LED IO word must return the current LED value (make the register readable). Memory map: monitor code and stack in the first 1 KB; user programs are loaded at 0x400 and up. Bench `tb/monitor_tb.v`: through the bench's serial TX/RX models, check `V`, write 8 words at 0x400 and read them back, `G` a small uploaded routine that sums them into a fixed address and returns, read the sum back, write the LED word and read it back, and an unknown command. Bytes must be handled at full 115200 rate with no gaps required between them.

- [ ] **Exportable hardware test programs.** `tb/hwprogs_tb.v` assembles a set of self-contained test programs with the macros — at least: the ALU sweep with fixed vectors, every load/store width and offset, fib/gcd, a jump/branch torture — each loaded at 0x400, ending by writing a result block (a signature word `0x600D0000 | index` followed by its result words) at 0x800 and returning with `ret`. The bench runs each program through the RTL via the monitor (upload with `W`, run with `G`, read the block with `R`) and checks the results against hand-computed expectations. Then it `$writememh`s, per program, the program words and the expected result block to `build/hwprogs/<name>.prog.hex` and `<name>.expect.hex` for the host tool. Add `hwprogs` to `make sim` outputs (the Makefile rule for benches already runs it; just make sure `build/hwprogs/` exists — create it from the bench with `$system` if needed, or write into `build/` directly with fixed names).

# Phase 4 — visual verification (parked; not needed until the SoC has a visual peripheral)

Idea, not yet a task: a fixed webcam over the board as a verifier for outputs that have no register to
read back (OLED, LED matrix, VGA). Capture a frame (`imagesnap`/`ffmpeg` — one extra tool), then either
pixel-compare fixed regions against an image rendered by the simulation (deterministic, alignment-
sensitive) or hand the frame to a vision-capable model with a yes/no question (robust, fuzzy). For the
five LEDs the UART monitor (phase 3) is the better sensor; revisit this when the first visual peripheral
lands. Not a `- [ ]` item on purpose — the loop must not pick it up.
